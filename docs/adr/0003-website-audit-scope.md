# website-audit crawls a whole site and defines its own rubrics, unlike its page-level siblings

Every other audit-style skill in this collection (`staleness-audit`, `alt-text`, `geo-audit`) operates on a single page of pasted or fetched content and judges it against a fixed rubric. `website-audit` was requested to cover a broader set of criteria — Brand, Quality, Accessibility, GDPR, Ownership, Up-to-date, Audience size/analytics, and Duplication — and several of these (Ownership, Audience, Duplication) are meaningless at single-page granularity: "who owns this site" and "does this exist elsewhere in the estate" are estate-level questions by definition.

This forced two departures from the established pattern:

1. **Unit of work is a website, not a page.** The skill performs a bounded crawl from a starting URL (sitemap-first, falling back to a capped breadth-first link crawl — default ~25 pages / depth 2, always stated in the output) rather than accepting a single page of pasted content. When no fetch/crawl tool is available, it falls back to asking for a supplied list of page URLs or pasted pages, mirroring the "no web access fallback" pattern already used by `graduate-outcomes`.
2. **Self-contained rubrics, not reused ones.** Accessibility and Up-to-date overlap with `alt-text`'s WCAG rubric and `staleness-audit`'s flagging logic respectively. We considered having `website-audit` orchestrate those skills as sub-checks (one shared source of truth), but chose independent, purpose-built rubrics instead: `website-audit`'s Accessibility and Up-to-date checks are scoped to what a bounded multi-page crawl can assess (markup-level signals only, no visual rendering), which isn't quite the same shape as a single deep page-level audit. The trade-off, accepted deliberately: the WCAG and staleness logic now exists in two places in this repo and can drift apart over time. If that drift becomes a real maintenance burden, revisit and have `website-audit` call out to `alt-text`/`staleness-audit` per crawled page instead.

Also unlike its siblings, legal/policy pages (privacy policy, cookie policy) discovered during the crawl are always fetched for content inspection regardless of the page/depth budget — otherwise the GDPR criterion could never reach Green on a compliant site simply because the crawl radius never reached `/privacy`.
